# Spike 2 結果：右窗格無焦點時的 CDP 輸入注入

量測日期：2026-08-31
Electron 版本：44.0.0
每種狀態次數：200

## 現行結論（最終，2026-09-01 解鎖環境實測）

判準 99%：**通過**。三種焦點狀態全部 200/200 = 100.0%，且腳本的有效性閘門判定
「量測有效：三種焦點狀態確實互不相同」。

| 焦點狀態 | 視窗 isFocused | 左窗格 | 右窗格 | 成功次數 | 成功率 | 判準 99% |
|---|---|---|---|---:|---:|---|
| 右窗格聚焦 | true | false | true | 200/200 | 100.0% | 通過 |
| 左窗格聚焦（使用者在打字） | true | true | false | 200/200 | 100.0% | **通過** |
| 整個視窗失焦（`app.hide()`） | false | false | false | 200/200 | 100.0% | **通過** |

判準關心的是後兩種狀態，兩者都是 100%。

**這代表什麼**：CDP 的 `Input.*` 在右窗格沒有焦點時、甚至整個視窗失焦時，注入都完全可靠。
規格 §8 對這個 spike 的假設（「agent 在背景跑、使用者同時在左窗格打字」）成立，
不需要採用 §8 已備妥的降級方案（agent 操作期間把焦點移到右窗格並在左窗格顯示遮罩）。

執行環境：macOS 螢幕已解鎖、yeschef 未同時執行。Electron 44.0.0。
輸出中出現的 `LatencyInfo vector size ... is too big` 是 Chromium 對 200 次連續注入的
合成器警告，與注入成功與否無關，三種情境的計數皆完整回收。

**下方「狀態：BLOCKED」一節記錄的是 2026-08-31 螢幕鎖定時的無效量測，已被本節取代。**
那一節保留的價值在於：它證明有效性閘門在該擋的時候會擋（三種狀態的 isFocused 全部相同、
結束碼 1）。加上本次通過，這道閘門在兩個方向都驗證過。

## 狀態：BLOCKED — 量測跑完了，但數字不能用來做判準（已被上方「現行結論」取代）

腳本本身可執行完畢，三個情境都印出成功率，見下表。但這次量測**沒有滿足
brief 明訂的有效性前提**：「焦點狀態要真的切換到，你要能證明，不能只是呼叫
了 focus() 就假設成功」。

### 發生什麼事

執行環境的 macOS 螢幕處於鎖定狀態（用 `ioreg -n Root -d1 | grep CGSSessionScreenIsLocked`
查得 `CGSSessionScreenIsLocked=Yes`，且 `HIDIdleTime` 顯示已閒置約 3.8 小時，
沒有人實際坐在螢幕前）。

macOS 鎖定畫面期間，loginwindow session 獨佔 WindowServer 的焦點仲裁，任何
一般應用程式都無法成為 frontmost/key window，這與程式本身無關。用以下三步
驗證過這不是腳本的 bug，而是環境限制：

1. 在 `run()` 一開始加了 `win.show()` + `app.focus({ steal: true })` +
   `win.focus()`，等 300ms 後查 `win.isFocused()`：結果仍是 `false`。
2. 用獨立診斷腳本（10 次、每 500ms 查一次）確認不是時序問題：10 次全部
   `isFocused=false`。
3. 用 `osascript -e 'tell application "Finder" to activate'` 測試「連
   Finder 都叫不到前景」——與 Electron 或本腳本完全無關的對照組，結果
   frontmost process 仍是 iTerm2。三個對照都指向同一個結論：鎖定畫面期間
   整個 session 無法做任何視窗啟用（window activation）。

**腳本現在會自己抓到這件事，不需要人眼比對。** `probe-input-focus.ts` 內建
了一個有效性閘門（`checkValidity`）：三個情境跑完後，比對「整個視窗失焦」
的 `winFocused` 是否與「右窗格聚焦」不同、「左窗格聚焦」的
`terminalFocused`／`agentFocused` 是否與「右窗格聚焦」不同。任一項相同就代
表焦點根本沒切換過去，腳本會印出顯著的無效標記、逐條列出哪個比較失敗，並以
`app.exit(1)` 結束（非零結束碼）。這次因為螢幕鎖定，三項比對全部失敗，腳本
如實回報無效，見下方「本次實測輸出」。

每個情境切換焦點後，腳本不再固定等 300ms，改成每 50ms 輪詢一次焦點狀態，
最多等 3 秒（`pollUntilSettled`）：情境 1、2 等到目標窗格 `isFocused()`
變 `true`，情境 3 等到 `win.isFocused()` 變 `false`。逾時仍會繼續往下跑，
但會在該情境的診斷行加註「逾時 3000ms，狀態可能未穩定」，讓使用者能從輸出
分辨「真的切不過去」和「只是還沒等到」兩種情況——`app.hide()` 是跨程序、非
同步的 OS 層級操作，固定等待時間可能踩不準，輪詢比較能反映狀態真的穩定了。

另外把情境 3（整個視窗失焦）的做法從 `win.blur()` 改成 `app.hide()`：
Electron 文件對 `BaseWindow.blur()` 只保證「移除視窗的焦點」，不保證焦點會
轉移到別的應用，`app.hide()` 才是 macOS 上讓整個 app 離開前景的直接做法。
是否真的生效，一樣交給閘門用 `win.isFocused()` 驗證，不是假設。**但
`app.hide()` 量到的其實是「隱藏」，不是「僅僅失焦」**，這點在下方「情境 3
的一個解讀落差」另外說明。

### 這對數字的意義

三個情境的 focus 狀態證明行全部印出：

```
[右窗格聚焦] 焦點狀態：視窗 isFocused=false 左窗格 isFocused=false 右窗格 isFocused=false
[左窗格聚焦（使用者在打字）] 焦點狀態：視窗 isFocused=false 左窗格 isFocused=false 右窗格 isFocused=false
[整個視窗失焦] 焦點狀態：視窗 isFocused=false 左窗格 isFocused=false 右窗格 isFocused=false
```

三種情境在 OS 層級的實際焦點狀態完全相同（都是「整個視窗從未拿到焦點」），
呼叫 `agent.webContents.focus()` / `terminal.webContents.focus()` /
`app.hide()` 在 Chromium 或 macOS 層級確實各自留下了設定，但因為最上層
`BaseWindow` 從未成為 key window，這些呼叫沒有造成三種情境之間任何可觀察的
差異。換句話
說：這次跑出來的三行「100.0%」測的其實是同一件事——螢幕鎖定、視窗永遠拿不
到焦點時 CDP 是否還能注入——而不是 brief 要問的「右窗格聚焦 / 左窗格聚焦 /
整個視窗失焦」三種相異狀態下的差異。

**不能拿這三行數字去做 go/no-go 判斷。** 三行雖然都是 200/200，但這只回答了
一個比原題更極端也更窄的問題（螢幕鎖定時），沒有回答 brief 真正要問的問題
（使用者在左窗格打字、右窗格保有 view-level 焦點但非 OS 前景視窗時，CDP 是
否可靠）。

### 一次有效的執行長什麼樣

在螢幕解鎖、有實際互動 session 的環境下重跑，一次**有效**的執行必須同時符
合：

1. 三行 `焦點狀態：` 診斷輸出**必須互不相同**，具體來說：
   - 「整個視窗失焦」那行的 `視窗 isFocused` 要和「右窗格聚焦」那行不同
     （預期 `右窗格聚焦` 是 `true`、`整個視窗失焦` 是 `false`）
   - 「左窗格聚焦」那行的 `左窗格 isFocused` 與 `右窗格 isFocused` 都要和
     「右窗格聚焦」那行不同（預期兩者對調：左窗格從 `false` 變 `true`，
     右窗格從 `true` 變 `false`）
2. 三行診斷輸出**都不應該**帶有「（逾時 3000ms，狀態可能未穩定）」註記。
   若某一行帶了逾時註記，即使剛好通過了上面的比對，也代表那個情境的焦點
   狀態是在等滿 3 秒後才擷取，不是穩定生效的結果，建議重跑一次確認
3. 腳本最後印出 `量測有效：三種焦點狀態確實互不相同，以上成功率可用於判準`，
   **沒有**印出 `!!!! 量測無效 !!!!` 區塊
4. `echo $?`（緊接在 `npm run spike:input` 後執行）回報 `0`

只要上面任一項不符合，這次的成功率數字就不能拿來對 99% 判準——不需要重讀
這份文件的推理過程，看腳本自己印出的結論與結束碼就夠了。

### 情境 3 的一個解讀落差：「隱藏」不等於「僅僅失焦」

情境 3 現在用 `app.hide()`，這個 API 同時讓整個 app（含視窗）
`isVisible=false`。但 brief 描述的真實情境是「使用者切到別的 app，
yeschef 視窗仍然可見，只是失去 OS 焦點」——例如使用者按 `Cmd+Tab` 切到
瀏覽器查資料，yeschef 視窗還在螢幕上，只是不是最上層。這兩種狀態不等價，
後者是比較溫和的情況：視窗仍在渲染、仍然可見，只是不是 key window。

換句話說，情境 3 若量到偏低的成功率，那個數字反映的可能是「視窗被隱藏」
造成 CDP 注入失效（例如渲染程序被降頻或暫停），而不是「單純失去焦點」造成
的。這兩種原因對規格 §8 降級方案的意義不同：前者可能代表只要別讓 yeschef
視窗被隱藏就好，後者才是真的要處理「失焦但仍可見」的情況。

**建議**：解鎖後若情境 3 沒有達到 99% 判準，在採用降級方案之前，先用另一種
做法把情境 3 再量一次——把別的應用叫到前景（例如 `osascript -e 'tell
application "Finder" to activate'`），但不要對 yeschef 呼叫
`app.hide()`，讓 yeschef 視窗維持可見只是失去焦點。比較兩次的成功率，才
能確認低成功率是失焦造成的還是隱藏造成的。這個第二種量法不在本次程式碼異
動範圍內，留給拿到結果的人視情況決定要不要做。

## 結論

**無法判定（BLOCKED），不是通過也不是未通過。** 量測基礎設施（腳本、CDP、
click-counter fixture）都跑得動，缺的是一個沒有鎖定畫面的 macOS session 來
產生三種真正相異的焦點狀態。

需要在**螢幕解鎖、有實際互動 session** 的環境下重跑 `npm run spike:input`，
並確認三行 `焦點狀態：` 診斷輸出中至少「左窗格聚焦」與「整個視窗失焦」兩種
情境的 `視窗 isFocused` 或至少 view 層級的 focus/blur 事件確實與「右窗格聚
焦」情境不同，才能拿新的成功率數字去對 99% 判準。

在那之前，規格層級的問題（左窗格打字時 CDP 對右窗格的輸入注入是否可靠）維
持未解，不可預設為通過而跳過規格 §8 的降級方案設計。
