# 主廚驗收：介面檢查

日期：2026-10-02。狀態：已確認，待實作。

## 1. 目的

主廚目前只檢查一件事：回報引用的工具確實執行過且成功。介面類任務改了 CSS 或元件後，平台不會檢查成果，全看模型自己有沒有截圖、有沒有注意到問題。

這份規格讓平台在驗收階段，對 worker 改過的介面檔案跑一組固定規則。規則由 YesChef 自己實作，不呼叫外部工具，不花模型額度，同樣的輸入一定得到同樣的結果。

## 2. 範圍

做：

- 對本次任務改過的 `.css`、`.scss`、`.tsx`、`.jsx`、`.vue`、`.svelte`、`.html` 檔案做靜態掃描。
- 掃描結果放進驗收單元的提示，並顯示在主廚任務畫面。
- 驗收回報要逐條說明每個發現怎麼處理；說「已修正」的，平台重新掃描確認。

不做：

- 需要瀏覽器實際畫面才能判斷的檢查（對比、文字溢出、版面重疊）。這類檢查要啟動專案的開發伺服器，另外規劃。
- 掃描整個專案。只看本次任務改過的檔案，既有的問題不算在這次任務頭上。

## 3. 改過哪些檔案

worker 開始時已經會存一份開發基準（`development-baselines`，鍵是 `chef:<taskId>`），目前只給 diff 畫面使用。驗收單元開始前，平台用這份基準算出本次任務新增或修改的檔案，篩出上面列的副檔名，作為掃描範圍。

掃描範圍為空時（任務沒改介面檔案），跳過整個檢查，不在提示裡加任何內容。

## 4. 規則

第一版六條，每條有固定 ID、說明與建議改法。規則只看單一檔案的文字內容，不需要編譯。

| ID | 抓什麼 | 嚴重度 |
| --- | --- | --- |
| `side-stripe` | 卡片、清單項目、提示框加上大於 1px 的單側彩色框（`border-left`／`border-right` 寬度大於 1px）。`blockquote` 不算 | 警告 |
| `gradient-text` | `background-clip: text` 搭配漸層，做出漸層文字 | 警告 |
| `eyebrow-label` | class 名稱含 `eyebrow` 或 `kicker` 的元素，放在標題元素（`h1`～`h3`）前面 | 警告 |
| `tiny-text` | `font-size` 小於 11px | 錯誤 |
| `focus-removed` | `outline: none` 或 `outline: 0`，同一檔案沒有對應的 `:focus-visible` 樣式 | 錯誤 |
| `pure-black-white` | 大面積背景或文字用純 `#000`／`#fff`（不含邊框與陰影） | 警告 |

規則放在 `src/main/chef/ui-check/rules/`，一條規則一個檔案，每條附單元測試（有問題、沒問題、邊界寫法各至少一例）。

單一檔案可以用註解略過某條規則，並寫明原因：`yeschef-ui-ignore <規則 ID>: <原因>`。沒寫原因的略過不生效。

## 5. 結果怎麼送給模型

驗收單元的提示加一段 `<ui-check>`：

```
<ui-check>
本次任務改過的介面檔案有 3 項發現。每一項都要在回報的 uiFindings 說明處理方式。
F1 side-stripe src/components/Card.css:12  border-left: 4px solid var(--accent)
F2 tiny-text  src/components/Badge.css:3   font-size: 10px
...
</ui-check>
```

每項發現給一個本次任務內唯一的編號（F1、F2⋯），避免模型自己描述位置造成對不上。

## 6. 回報與平台檢查

`report_result` 加一個選填欄位 `uiFindings`：

```
uiFindings: [{ id: "F1", resolution: "fixed" | "kept", reason: string }]
```

回報 `completed` 時，平台檢查：

1. `<ui-check>` 列出的每個編號都要出現在 `uiFindings`，缺一個就拒絕回報，錯誤訊息列出缺少的編號。
2. `resolution: "fixed"` 的項目，平台重新掃描該檔案；同一條規則在同一個位置附近（前後 5 行）仍然成立，就拒絕回報。
3. `resolution: "kept"` 必須寫原因。嚴重度為「錯誤」的項目不能選 `kept`，要修或在程式碼加上第 4 節的略過註解（註解本身會被掃到並記錄原因）。

回報被拒絕時，錯誤會照現在的方式回到模型（工具錯誤），模型可以修正後再回報。

## 7. 畫面

主廚任務的詳細資料加一區「介面檢查」：列出每項發現、處理方式與原因。沒有掃描範圍時不顯示這一區。

## 8. 相容性

- 舊任務（沒有 `uiFindings` 欄位）照常讀取。
- 沒改介面檔案的任務，行為與現在完全相同。
- `error-intake-setup`、`error-fix` 這類有特定目的的任務也適用，因為它們也可能改到介面檔案。

## 9. 驗收

- 每條規則的單元測試。
- 主廚流程測試：改了含問題的 CSS 時，驗收提示有 `<ui-check>`；漏回報編號被拒；說 fixed 但沒修被拒；修好後通過。
- 實機一次：開一個主廚任務，要求在示範專案加一張帶單側粗框的卡片，確認驗收階段抓到並修正。跑兩次。
