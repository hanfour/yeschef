# 視窗分區:活動列、側邊欄、主分頁區、狀態列

- 日期:2026-09-11
- 狀態:三個增量已完成,RESULTS-18 到 21
- 觸發:使用者提出把視窗拆成四個區域,並問主分頁區能不能衍生「開啟側邊預覽」

## 1. 為什麼要改

2026-09-10 到 09-11 用 yeschef 連續跑了四個多小時的真實工作(mirage 的音訊量測與輸入法實作),
現況的四個問題被同一段使用暴露出來:

| 現況 | 實際踩到的 |
|---|---|
| 歷史清單寬度固定 280,釘死在對話窗格裡,而且只有 Claude 對話有 | codex 的歷史沒有地方放(`ConversationPane` 明寫「codex 對話不畫 Recents」) |
| 右窗格是主行程用絕對座標擺的 `WebContentsView`,固定各佔一半 | 它不能變成分頁,也不能收起來,寬度不能調 |
| 沒有狀態列 | 誰在忙、誰等批准、花了多少,散在分頁記號與每段對話的結尾。控制端整天是用程式讀 `busyTabIds` 與 `pendingTabIds` 才知道狀態 |
| 沒有任何地方畫得出圖片 | codex 的截圖只顯示路徑;右窗格的截圖工具回傳的圖也只當成文字 |

四個區域的命名本身沒有價值,值錢的是它解開的這四件事。所以這份設計不照搬整套編輯器的
模型,只做到能解決上表為止。

## 2. 目標與非目標

**目標**

- 一條狀態列:整個視窗一處看得到「誰在忙、誰等批准、目前這段對話花了多少」。
- 側邊欄能放多種內容,不是只有 Claude 的歷史清單。
- 主分頁區能放多個分頁,右窗格是其中一個;由此衍生「開啟側邊預覽」。

**非目標(這一輪不做)**

- 可拖曳停靠、多個面板群組、view container 那一整套。表面積大,上表四件事用不到。
- 活動列。側邊欄目前只有一種內容,列出來只有一顆圖示;等側邊欄有三種以上內容再說。
- 每個 agent 一個假桌面。理由見 §6。

## 3. 一個要先想清楚的耦合

右窗格是主行程建立的 `WebContentsView`,由 `index.ts` 的 `applyLayout` 用
`splitBounds(contentBounds, 0.5)` 擺位,視窗改變大小時重算。renderer 完全不知道它在哪裡。

主分頁區要能放它,方向就得反過來:**renderer 決定版面,主行程照著擺**。
renderer 量出主分頁區的內容矩形,經 IPC 告訴主行程,主行程 `setBounds`。
這是這次改動真正的成本,不是畫面上多幾個框。

配套的三件事:

- 矩形要用 CSS 像素,主行程換算成 `WebContentsView` 的座標;縮放與多螢幕由主行程負責。
- 分頁被切走或收起時,右窗格要能被藏起來(高度或寬度給 0 不夠,會留下可點的區域)。
- renderer 還沒量到之前,主行程先把瀏覽器藏著。原本寫的是「用對半切當初始值,不要留一塊空白」,
  但上次收起的話,先顯示再藏會讓右半邊白閃一下(2026-09-11 量兩次,176ms 與 184ms);
  而那段時間 renderer 的右半邊已經畫好深色的主分頁區,藏著並不會留下空白。

藏起來之後 agent 還能不能用這個瀏覽器,2026-09-11 用最小的 Electron 程式量過兩次,結果一致:

| 做法 | 截圖 | 頁面計時器(3 秒,正常 30 次) | `visibilityState` |
|---|---|---|---|
| `setVisible(false)`,預設 | 拿得到,內容是即時的 | 3 次 | `hidden` |
| `setVisible(false)` 加 `setBackgroundThrottling(false)` | 拿得到 | 30 次 | `visible` |

所以右窗格一律設 `setBackgroundThrottling(false)`,藏起來用 `setVisible(false)`。
不這樣做的話,使用者把右側收起時,agent 正在操作的頁面會降速到十分之一,
依賴計時器或動畫的頁面行為會跟使用者看得到時不一樣。

代價是右窗格在任何情況下都不降速:視窗縮到 Dock 或被別的視窗蓋住時,右窗格的計時器與動畫
照樣全速跑,開著重的網站會多吃 CPU 與電。

「只在 agent 有動作時關掉降速」2026-09-12 量過(兩輪,`docs/RESULTS-27-throttle-toggle.json`):
執行中 `setBackgroundThrottling(false)` 計時器立刻回到全速(3 秒 30 次)、切回 `true` 立刻降回 3 次,
但 `visibilityState` 不跟著變,藏著的時候一直是 `hidden`;它只在 view 建立當下依降速設定決定一次。
頁面若靠 `visibilitychange` 決定要不要暫停自己,執行中切換救不了它,會變成「計時器全速、頁面自認在背景」。
所以不做這個方案,維持一律關掉;要省電的話是另一條路(例如視窗縮到 Dock 時整個右窗格 `setVisible(false)` 並接受 agent 那時操作的頁面行為不同),沒有需求前不做。
CDP 截圖在藏著且降速開著時一樣拿得到即時內容,跟 §3 前一段的結論一致。

## 4. 三個增量

順序依「便宜且立刻有用」排。每個增量自己就是一個可用的東西,不必等下一個。

### 增量 1:狀態列

視窗底部一條,跨整個寬度,不隨分頁切換而變。

| 欄位 | 來源 | 沒有資料時 |
|---|---|---|
| 進行中 | `ProjectsView` 的 `busyTabIds`,跨全部專案數總數 | 不顯示 |
| 待批准 | `pendingTabIds`,跨全部專案數總數;點了跳到第一個 | 不顯示 |
| 同伴問答 | `usePeer` 的 `pending` 筆數 | 不顯示 |
| 目前對話 | 前景那個對話的輪數、花費、token | 還沒結束就只顯示輪數 |

不新增任何 IPC:四個欄位的資料 renderer 都已經有了(`projects:state`、`peer:state`、
以及對話自己的 `view.cost`)。

「待批准」要能點:點了切到那個專案與那個對話。這正是第二階段補的跨對話批准路由,
狀態列只是給它一個看得見的入口。

### 增量 2:側邊欄能放多種內容

現在 `ConversationPane` 直接畫 `Recents`,而且 `provider === 'codex'` 就整個不畫。
改成側邊欄是一個容器,內容由目前的對話決定:

- Claude 對話:歷史清單(現況)。
- codex 對話:目前沒有內容,顯示一句「codex 的歷史清單還沒做」,不是整個消失。
  codex 的 thread 在 `~/.codex/sessions`,是另一套格式,要新的資料來源,那是另一個子專案。
- 寬度可調並記住,不再寫死 280。

這一步不做新的資料來源,只把「側邊欄」從對話窗格裡拆出來,讓之後的內容有地方可放。

### 增量 3:主分頁區與側邊預覽

拆成兩步。3a 只做容器與瀏覽器分頁,把 §3 那個耦合翻轉做完;3b 在容器裡加預覽分頁。
3a 做完的時候畫面上多一條只有一個分頁的分頁列,這是刻意的,容器先到位 3b 才有地方放。

3a 不做寬度拖曳。主分頁區與左邊的分界線緊貼著右窗格這個原生 view,滑鼠一越過分界
事件就進了另一個 webContents,renderer 的 pointer capture 收不收得到要另外量,
量過之前不排進來。3a 維持現在的左右各半。

2026-09-12 量過(`spike-divider`,真實滑鼠用 cliclick):越過分界後 renderer 一個 move/up 都收不到,
pointer capture 無效;把右邊 view 藏掉也沒用,因為 spike 裡那塊區域底下沒有任何 view。
但 yeschef 的 renderer 本來就佔滿整個視窗,瀏覽器只是疊在上面,所以拖曳期間把瀏覽器藏起來
(`useReportBounds` 回報 null 那條既有的路),游標底下就只有 renderer,事件不會斷。
分隔條依此做,計畫 `docs/superpowers/plans/2026-09-12-panel-divider.md`。

主分頁區的分頁列。第一批分頁:

- 瀏覽器(現在的右窗格)。
- 預覽:顯示一個檔案。第一版只支援圖片與 Markdown,因為那兩種是現在完全畫不出來的。

「開啟側邊預覽」= 在主分頁區開一個預覽分頁。來源有兩個:對話裡的截圖工具結果,
以及專案裡的檔案。roadmap 第 2 項的預覽從來沒做,這一步接回它。

3b 的設計依據(2026-09-11 實際攔下 renderer 收到的事件看過):

- 截圖工具的結果到 renderer 是 Anthropic API 的 image block:
  `{ type: 'image', source: { type: 'base64', media_type: 'image/png', data } }`,跟一段文字放在同一個陣列。
  live 與重開 app 後從逐字稿載入,兩條路的形狀一樣。
- 目前 `ToolCall` 把結果一律 `JSON.stringify` 進 `<pre>`,展開一張截圖的 tool block 會看到五萬多字的 base64。
  所以 3b 第一件事是讓對話裡的圖片直接畫出來,預覽分頁是第二件。
- renderer 在沙箱裡不能讀檔。專案檔案的預覽要一條新的 invoke 頻道,主行程負責三道檢查:
  路徑解析成 realpath 之後必須在專案資料夾內(擋掉 `..` 與符號連結跳出去)、副檔名只收圖片與 Markdown、
  檔案大小有上限。
- 入口放在對話裡:截圖縮圖旁一顆「在側邊預覽開啟」,以及參數帶檔案路徑的工具(Write、Edit 的 `file_path`,
  codex 截圖的 `path`)在副檔名可預覽時多一顆「預覽」。沒有檔案樹,那是另一件事。

主分頁區整個可以收起,收起時左邊佔滿整個視窗。

## 5. 驗收(三個增量各自的)

增量 1:一個對話在跑、另一個對話等批准時,狀態列同時顯示兩個數字;點「待批准」會切到
那個對話而且那張卡在畫面上;對話結束後花費出現在狀態列,不必捲到對話底部。

增量 2:切到 codex 對話時側邊欄不是消失而是有一句說明;拖動側邊欄寬度,重開 app 之後
寬度還在。

增量 3a:把主分頁區收起,左邊佔滿而且瀏覽器不見;展開後瀏覽器回到原位;
視窗改變大小之後瀏覽器分頁的位置仍然對齊它的內容矩形;收起的狀態重開 app 後還在。

增量 3b:展開一張截圖的 tool block,看到的是圖不是 base64;從那張截圖開一個預覽分頁,圖真的畫出來,
瀏覽器分頁切走時瀏覽器藏起來;agent 寫一份 Markdown 之後按「預覽」,分頁裡是排好版的內容;
要求預覽專案資料夾外面的檔案,得到說明而不是檔案內容。

## 6. 為什麼不做「每個 agent 一個假桌面」

使用者同時提了這個。這裡記下不做的理由,免得之後重問。

那個提議把兩件事混在一起。**隔離**那一半已經有了:codex 跑在 `workspace-write` 沙箱裡,
每個子專案有自己的 git worktree;要再加的是程序與連接埠的隔離,那是容器或約定的事,
不需要桌面。

**圖形環境**那一半才是提議的重點,而它解不了實際卡住的那件事。2026-09-11 的 mirage 輸入法
工作裡,codex 自己驗完了 Android 那一側(截圖、欄位比對、60 個案例);唯一需要人的是
「用真正的 Mac 輸入法按實體鍵」。假桌面如果是 Linux 加虛擬顯示,與那件事無關;
如果是 macOS 虛擬機,在裡面驅動一個真的輸入法跟在本機一樣難,難的不是桌面而是輸入法那條路。

真正會有幫助的是另一件事,範圍也小得多:讓 agent 在人監督下驅動這台機器的 UI。
那是權限與安全的問題,不是沙箱的問題,要做的話另立子專案。
