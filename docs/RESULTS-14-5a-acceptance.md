## 2. 驗收抓到的缺陷

### 2.1 對方在背景時,排隊的提問會被丟掉(已修,並重驗)

1456 條單元測試、六個 Task 的審查加一輪 opus 全分支審查都沒有抓到。

現象:A 問 B,B 正在跑回合而且是背景對話。B 的回合結束時注入送出,但那段文字沒有進到 B,
主行程只留下一行 `agent:input:輸入到達時 session 已不在 live,這則輸入未送出`。
提問方等滿 10 分鐘拿到逾時錯誤,B 從頭到尾不知道有人問過。

成因是背景對話的 sleep 與注入之間的競態。`notifyIdle` 由 `onBusyChange(false)` 觸發,
那個時點 sleep 還沒 dispatch,所以 `conversation.ts` 的 `userInput` 看到的 `state` 還是 live,
把送出排進 effects 鏈;等那個 effect 真的執行時對話已經睡了,
`state.kind !== 'live'` 那個分支就把文字丟掉。

人自己打字碰不到這條路:人只能對前景對話打字,而前景對話不會 sleep。同伴注入會碰到。

修法:那個分支不再丟掉文字,改成重新送一次(走與「對非 live 對話送輸入」相同的既有 resume 路徑),
只重試一次,第二次仍然送不出去才記錯誤。

重驗:換乾淨的 fixture,先確認 renderer 的 `busyTabIds` 顯示 B 在忙,才切到 A 提問。
B 的回合結束後提問自成一輪出現,答案回到 A,主行程沒有再出現「輸入未送出」那一行。
非 live 那條路是把文字當 `initialInput` 交給 resume,所以畫面上只出現一次,不會重複。

### 2.2 yeschef 自己的 MCP 工具結果會多畫一個「未知事件」

`ask_peer` 與 `answer_peer` 的工具結果,在畫面上除了正常的 tool block 之外,
還會多出一個可展開的「未知事件」,裡面是工具回傳的內容陣列
(例如 `[{"type":"text","text":"已回答"}]`)。

成因在 `src/shared/events.ts` 的 `rawOutputEvents`:它預期 `tool_use_result` 是字串或物件,
程序內 MCP server 給的是內容陣列,兩個分支都不符就走 `unknownEvent`。
這個檔這一支完全沒動過,右窗格那八個工具走的是同一條路,所以不是 5a 帶進來的,
但 5a 讓它更常出現。留給第二階段的畫面一起處理。

### 2.3 一次沒能重現的分頁與 thread 錯亂

第一輪驗收結束時,A 的分頁被指到一個新建的 thread,而那個 thread 裡裝的是 B 的 session id。
之後 A 的 `ask_peer` 就把自己的 `from` 寫成 B 的 linkId,問到自己身上。

狀態檔留下的形狀(新 thread + 分頁改指 + thread 裡只有一個既有 session)與
`pointConversationAt`(開啟歷史對話走的那條路)一致,不是 `recordStarted` 的形狀。
換乾淨的 fixture 重跑兩輪、每 0.5 秒記一次狀態檔,都沒有再出現。
成因未定位,需要另外查一次,不在這一階段的範圍。

## 3. 一併記下的既有行為

- 回答方在背景時,它要用的工具批准會被扣住(規格 §6.3 已寫明)。驗收時 B 在背景卡在
  Bash 批准上七分鐘,提問方只能等。實務上「問一個不需要工具就能答的問題」才會順。
- 只有一個同伴時,`to` 給錯仍然回錯誤並列出那一個候選;模型看到錯誤訊息裡的 8 碼 id 之後
  自己重試就成功了。錯誤訊息帶候選是有用的。
- 本次開機從未被切到前景的對話不會有核心,也就不在同伴清單裡。三個對話要各自跑過一輪
  才會互相看得見。
