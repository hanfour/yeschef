# 主廚自動選模型、委派與故障接手

狀態：2026-09-21 已實作第一版主廚控制台、序列委派與有界故障改派。下文保留完整目標契約，未代表全部能力已交付；實作範圍、驗證結果與未完成項目見 [第一版驗收紀錄](LOCAL-ACCEPTANCE-AUTO-CHEF-2026-09-21.md)。

## 目標與目前缺口

使用者只交付目標，不必指定 model。YesChef 主廚依可用模型與任務需要委派工作；某個模型故障時，任務能帶著已完成的成果接續，而不是綁死在原 session。

目前分頁綁定 Claude／Codex provider，模型沿用後端設定。雖然 ThreadEntry 已預留 switchPhase、handoffVersion 與 session chain 欄位，但沒有自動模型路由或完整跨 provider 故障接手機制。peer 問答也只會找到已登錄且有 session 的對話，不會自行規劃並建立工作者。

## 使用介面

新任務提供：

- 自動（主廚）：使用者設定允許的模型池、品質／成本偏好與任務預算，不必指定 model。
- 偏好模型＋自動備援：優先用指定模型，故障時允許改派。
- 固定模型：不自動切換，保留手動控制。

自動模式是 task 的執行策略，不是新增一個叫 auto 的 provider。既有固定對話不偷偷改成自動。工作台顯示目前執行者、實際 model、選擇／改派原因、進度、已消耗用量、交接與重試紀錄。

## 三個獨立責任

| 元件 | 責任 |
| --- | --- |
| 任務管理器 | 持久保存目標、授權、成果與狀態；主廚 model 故障時也不丟任務 |
| 主廚／路由器 | 拆分任務、提出所需能力，從合格池中選擇模型並委派 |
| 工作者 adapter | 使用 Claude／Codex 執行單一工作單位，回報真實模型、工具結果、diff、測試與失敗原因 |

主廚是一個可接手的角色，不等於永遠綁定某個 LLM session。模型選擇不能只依固定的模型名稱對照表；需由 provider 的模型列表／能力資訊與實際健康狀態建立模型池，記錄 requested model 與 session/init 回報的 actual model。

## 路由規則

1. 先排除未連線、未登入、使用者未允許、缺少必要工具／圖片／上下文能力、超出預算或處於故障冷卻期的候選。
2. 依工作單位的需求（分析、程式修改、測試、文件、審查）及成本／品質偏好選擇；可加入有資料支撐的近期成功率與延遲，不能憑模型名稱假造能力或分數。
3. 同一工作單位進行中維持執行者，直到完成、安全交接或可確認的執行故障，不逐 token／每個工具呼叫切換模型。
4. 指定必要能力找不到合格候選時顯示阻塞原因，不默默使用不合格模型。

## 故障接手規則

| 狀況 | 處理 |
| --- | --- |
| 暫時網路／服務錯誤、可辨識的 rate limit | 有界重試與退避；超限後選其他合格候選 |
| 模型不可用、該連線額度用盡／登入失效 | 暫停該候選並改派其他已授權且已連線候選 |
| 長時間工具執行但仍有心跳 | 顯示正在執行；不能只因沒有文字串流就判定模型壞掉 |
| 測試失敗、程式錯誤 | 當成工作結果進入修正迭代；不以換模型掩蓋失敗 |
| 等待批准、使用者拒絕、使用者停止 | 保持該狀態，不靠改派繞過批准或重啟使用者已停止的工作 |
| 所有候選失敗或預算耗盡 | 任務轉為可恢復的 blocked 狀態，明示原因，避免無限重試 |

首版每個工作單位最多 2 次自動改派，整體受任務預算與期限限制。暫時失敗分類使用 adapter 的結構化錯誤；無法判定原因時保留證據，不把任何 session-end error 都當成模型故障。

## 接手前必須做的事

- 確認舊 worker 已停止，或已撤銷它的寫入租約；未確認前不讓另一 worker 同時接管同一份工作目錄。
- 保存 checkpoint：原始需求、已完成／未完成步驟、repo／worktree／branch／HEAD、寫檔紀錄、測試結果、附件引用、批准與拒絕狀態、未結束工具。
- 新 worker 先核對現況再續接，不把整段原始 prompt 盲目重跑。
- 對 push／建立 PR／發布文件等操作，保存操作 ID 與執行結果。逾時而不知道是否成功時，先查詢實際狀態；無法確認就停在 reconciliation，不重複副作用。
- 不跨 provider 傳遞原生 session ID 當作 resume。以平台 task ID、交接摘要及成果引用建立新執行 session。
- 同一 repo 的寫入／Git index 操作持有租約；需要並行時使用隔離 worktree，再由主廚整合與驗證。

## 委派來源與 diff

所有平台委派都以正式 task registry 記錄 parentTaskId → childTaskId → provider/session/model → repositories/tool results。主廚的 diff 清單取自整棵授權任務樹的成功寫檔紀錄，不能只看父 session 的工具卡，也不能把整個 Workspace 目錄的 dirty 狀態當作證據。

應提供結構化 delegate_task 工具，由平台建立工作者、選模型、保存來源及回收資源。避免主廚透過未登錄的 Bash 啟動外部 agent，導致來源與恢復狀態失聯。舊有 codex exec 工作可依可驗證的父呼叫、輸出 session ID、子執行紀錄與成功 patch 做有限補回；無法驗證的來源明示不完整。

## 授權與交付

自動選模型不增加檔案、命令、網路、PR 或發布權限。每位 worker 仍經同一授權／審核服務。使用者的拒絕不能因換模型而失效；主廚不得自行擴大模型池與資料可交付的 provider 範圍。

完成判準由 task 保存：必要修改、實際跑過的驗證、已知失敗／限制及交付文件。worker 宣稱完成不等於平台驗收完成。實際用量以 provider 回報保存；預算控制不得把估算金額顯示成已收費金額。

## 實作順序與驗收

1. 平台 TaskRun／ExecutionAttempt／Checkpoint／DelegationLink 與持久化狀態機，支援 crash recovery。
2. 模型清單與健康／能力 adapter；新任務的 Auto／Preferred／Pinned 設定。
3. 主廚 delegate_task、worker 建立／回收、工作目錄租約及來源關聯。
4. 單工作單位的有界重試、跨模型交接、未知副作用調查與預算停止。
5. UI 任務樹／改派理由／實際 model／手動接管；diff 彙整整個任務樹。

必要驗收：模型 429／斷線／程序退出能改派且不丟成果；批准與使用者停止不觸發改派；舊 worker 未終止時不產生雙寫；PR 建立逾時不重複建立；父子任務跨 provider 修改可正確出現在父任務 diff；重啟可恢復 blocked／running 任務且不誤報完成。

## 現有程式介接

新工作者應由平台呼叫既有 runtimeFor 工廠與共用批准 registry，繼承 Skills、工具與專案權限。任務層與 provider session 分離，改派時建立新的 execution slot，再將實際 provider／model／session 加入 task chain；不在舊 worker 尚未停止時直接改寫原分頁的 provider。
